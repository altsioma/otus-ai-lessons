## Prompt 1
Мы выполняем домашнее задание «Простой MCP-сервер» с нуля.

### Что нужно определить

1. **Стек**
   - Выбери язык, MCP SDK и менеджер пакетов.
   - Предпочтительно используй TypeScript и официальный MCP SDK для TypeScript, если нет веских причин выбрать другой стек.
   - Обоснуй выбор кратко, без сравнения большого количества альтернатив.

2. **Практический сценарий**
   - Предложи один конкретный сценарий использования MCP-сервера для разработки.
   - Определи 3–4 инструмента с понятными назначениями, входными параметрами и структурированными результатами.
   - Выбери инструменты, которые можно легко проверить на демонстрационных данных.

3. **Архитектура**
   - Выбери транспорт MCP: stdio или HTTP.
   - Предложи минимальную структуру файлов проекта.
   - Определи, где будут реализованы сервер, инструменты, контракты результатов, логирование и тесты.
   - Предусмотри ограничения безопасности, если инструменты читают файлы или выполняют команды.

4. **Интеграция с IDE**
   - Основной приоритет — подключение к Claude Code, если оно подходит для демонстрации задания.
   - Предложи воспроизводимую конфигурацию MCP и команду запуска.
   - Учти, что фактический вызов инструментов из IDE обязателен: простого тестирования MCP-сервера из терминала недостаточно.

5. **Проверка критериев приёмки**
   План должен предусматривать:
   - минимум 2 работающих инструмента, целевой вариант — 3–4;
   - описания, схемы входных параметров и структурированные результаты;
   - серверные логи с именем инструмента, входными параметрами без секретов и статусом выполнения;
   - не менее 5 проверочных запросов к агенту, из которых минимум 3 вызывают MCP-инструменты;
   - сохранение фактических подтверждений вызовов в репозитории;
   - README с инструкцией запуска и подключения;
   - `.env.example`, если конфигурация требует переменных окружения;
   - ссылки на реализацию, логирование и контракты с актуальными диапазонами строк;
   - тестирование и проверку отсутствия секретов в Git.

### Формат ответа

1. Выбранный стек и обоснование.
2. Сценарий и список инструментов.
3. Предлагаемая структура проекта.

## Prompt 3

Продолжай реализацию MCP-сервера в текущем каталоге.

На этом этапе реализуй демонстрационные данные, контракты и четыре инструмента. Интеграцию с IDE пока не настраивай.

## 1. Демонстрационные данные

Создай внутри `HW-4/`:

- `demo-project/` — небольшой TypeScript-проект с модулем корзины, например `src/cart.ts`, связанными функциями и тестами;
- `docs-kb/` — 3–4 Markdown-документа с правилами демонстрационного проекта, например округление цен, скидки и обработка ошибок.

Данные должны быть небольшими, согласованными между собой и подходить для воспроизводимой проверки всех инструментов.

## 2. Контракты

Создай `src/contracts.ts` с Zod-схемами входных параметров и структурированных результатов всех инструментов.

Для каждого инструмента определи:
- имя и назначение;
- схему входных параметров с ограничениями;
- схему успешного результата;
- единый формат ошибок с кодом и сообщением.

Используй API установленной версии MCP SDK. Не выдумывай поддержку параметров или форматов, которых нет в установленной версии.

Опиши контракты также в `docs/contract.md`. Документация и фактические Zod-схемы должны соответствовать друг другу.

## 3. Реализация инструментов

Реализуй четыре инструмента в отдельных файлах:

1. `search_code` — поиск текста в файлах демонстрационного проекта с указанием пути, строки и совпавшего фрагмента.
2. `get_file_outline` — получение публичных экспортов TypeScript-файла: имена, типы экспортов, номера строк и доступные сигнатуры.
3. `lookup_docs` — поиск по Markdown-документам `docs-kb/` с указанием источника, заголовка, диапазона строк и фрагмента.
4. `run_check` — запуск только заранее разрешённых проверок демонстрационного проекта.

Для каждого инструмента:
- используй отдельную функцию реализации;
- зарегистрируй инструмент через API установленного SDK;
- объяви схемы входа и выхода;
- возвращай структурированный результат, соответствующий контракту;
- обрабатывай ошибки предсказуемо и документированно.

Для `get_file_outline` используй TypeScript Compiler API установленной версии TypeScript. Не пытайся извлекать сигнатуры регулярными выражениями, если доступен AST.

Для `lookup_docs` достаточно детерминированного поиска по заголовкам и содержимому. Не добавляй внешние API, embeddings или сетевые зависимости.

Для `run_check` используй фиксированный перечень команд и аргументов. Запрещены произвольные команды, shell-строки и пользовательские аргументы командной строки. Используй `execFile` или эквивалентный безопасный запуск без shell, ограничь время выполнения и размер возвращаемого вывода.

## 4. Безопасность

Реализуй `src/security/sandbox.ts`.

- Все файловые операции должны оставаться внутри разрешённых каталогов проекта.
- Проверяй нормализованные пути и реальные пути с учётом симлинков.
- Запрещай доступ к `.env`, `.git`, `node_modules`, приватным ключам и другим явно исключённым файлам.
- Ограничь размер читаемых файлов и число возвращаемых результатов.
- Проверяй таймауты и корректно обрабатывай отсутствующие файлы.
- Не раскрывай содержимое секретов в сообщениях об ошибках и логах.

Не полагайся только на проверку строки пути до открытия файла. Проверь, что реализация не допускает обход ограничений через `..` и симлинки.

## 5. Логирование

Добавь `src/withLogging.ts` или эквивалентную общую обёртку для всех инструментов.

Каждый фактический вызов должен порождать структурированную запись с:
- именем инструмента;
- входными параметрами после редактирования чувствительных значений;
- статусом `success` или `error`;
- длительностью выполнения;
- кодом ошибки при неудаче.

Логи направляй в stderr и, при необходимости, в локальный файл, не попадающий в Git. stdout оставь исключительно для MCP-протокола.

## 6. Тесты

Добавь тесты на `node:test` для каждого инструмента, контрактов и безопасности.

Обязательно проверь:
- успешные вызовы каждого инструмента;
- пустые результаты поиска;
- отсутствующие файлы;
- некорректные параметры;
- path traversal через `../`;
- попытку чтения запрещённых файлов;
- симлинк, ведущий за пределы разрешённой директории;
- отказ от произвольной команды в `run_check`;
- таймаут проверки;
- соответствие возвращаемых результатов схемам;
- наличие логов успешных и ошибочных вызовов.

Добавь интеграционный тест через MCP Client установленного SDK: `tools/list` должен содержать все четыре инструмента, а `tools/call` должен возвращать корректный результат.

## 7. Проверка и итог

Выполни сборку, проверку типов и весь набор тестов. Не ограничивайся успешной компиляцией: исправь обнаруженные проблемы безопасности и несовпадения контрактов.

В конце предоставь:
1. Список созданных файлов.
2. Контракты четырёх инструментов.
3. Результаты тестов и сборки.
4. Обнаруженные ограничения или нерешённые вопросы.
5. Краткое описание модели безопасности.

Не настраивай `.mcp.json`, не запускай демонстрацию из IDE и не заявляй о выполнении этих требований на данном этапе. После завершения остановись и дождись следующего задания.

9. **Доказательства.** Сошлись на существующие файлы в `evidence/`: трассы, серверные логи и скриншоты. Объясни, что трассы и логи подтверждают фактические вызовы, а тесты — корректность проверяемого поведения. Не представляй CLI-вызовы как вызовы из IDE.
